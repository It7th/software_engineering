# Проектирование документной модели LMS

Вариант 19: система управления обучением, близкая по смыслу к Moodle. В этой работе я не пытался один в один скопировать Moodle: там огромная зрелая схема, а для лабораторной важнее показать нормальную документную модель под заданные операции.

## Что нужно хранить

В задании есть три главные сущности:

- пользователь;
- курс;
- урок.

Но для операции “записать пользователя на курс” нужна еще одна сущность: запись на курс. Если хранить ее просто массивом внутри пользователя или курса, быстро становится неудобно обновлять статус, прогресс и проверять повторную запись. Поэтому в модели четыре коллекции:

- `users`
- `courses`
- `lessons`
- `enrollments`

## Коллекция `users`

Пример документа:

```js
{
  _id: ObjectId("660000000000000000000004"),
  login: "petrov",
  name: {
    first: "Павел",
    last: "Петров"
  },
  email: "pavel.petrov@example.com",
  passwordHash: "sha256:student001-just-for-lab",
  role: "STUDENT",
  status: "ACTIVE",
  profile: {
    city: "Москва",
    interests: ["backend", "api"]
  },
  createdAt: ISODate("2026-02-10T10:00:00Z")
}
```

`name` и `profile` сделаны embedded documents. Имя почти всегда читается вместе с пользователем, а профиль небольшой и не живет отдельно. Делать для этого отдельные коллекции было бы лишней нормализацией.

Индексы:

```js
db.users.createIndex({ login: 1 }, { unique: true })
db.users.createIndex({ email: 1 }, { unique: true })
db.users.createIndex({ "name.first": 1, "name.last": 1 })
```

## Коллекция `courses`

Пример документа:

```js
{
  _id: ObjectId("661000000000000000000001"),
  slug: "mongodb-for-lms",
  title: "MongoDB для LMS",
  description: "Документная модель, индексы и запросы на примере учебной платформы.",
  authorId: ObjectId("660000000000000000000002"),
  status: "PUBLISHED",
  tags: ["mongodb", "database", "backend"],
  settings: {
    language: "ru",
    difficulty: "beginner",
    certificate: true
  },
  createdAt: ISODate("2026-03-01T09:00:00Z")
}
```

`settings` встроены в курс, потому что это свойства самого курса. `tags` тоже массив внутри курса: они маленькие, часто читаются вместе с карточкой курса и не требуют отдельной жизни.

`authorId` является reference на `users`. Преподаватель может вести много курсов, его данные могут меняться, и дублировать имя/почту преподавателя в каждом курсе не хочется. В UI при необходимости можно сделать `$lookup`, а в списке курсов обычно достаточно `authorId`.

Индексы:

```js
db.courses.createIndex({ slug: 1 }, { unique: true })
db.courses.createIndex({ status: 1, createdAt: -1 })
db.courses.createIndex({ authorId: 1 })
```

## Коллекция `lessons`

Пример документа:

```js
{
  _id: ObjectId("662000000000000000000001"),
  courseId: ObjectId("661000000000000000000001"),
  title: "Зачем LMS документная модель",
  description: "Сравниваем таблицы и документы на живом домене.",
  position: 1,
  durationMinutes: 35,
  content: {
    blocks: [
      { type: "text", value: "Вводная часть" },
      { type: "quiz", questions: 4 }
    ]
  },
  status: "PUBLISHED",
  createdAt: ISODate("2026-03-11T09:00:00Z")
}
```

Уроки вынесены в отдельную коллекцию и связаны с курсом через `courseId`. Теоретически их можно было бы embedded-массивом хранить внутри курса, но для LMS это не самый удачный вариант: уроков может быть много, их редактируют отдельно, у них появляется контент, тесты, длительность, статус публикации. Один документ курса со временем стал бы большим и шумным.

А вот `content.blocks` встроен в урок. Блоки контента принадлежат только одному уроку и обычно читаются вместе с ним.

Индексы:

```js
db.lessons.createIndex({ courseId: 1, position: 1 }, { unique: true })
db.lessons.createIndex({ courseId: 1, status: 1 })
```

Уникальность пары `courseId + position` защищает курс от двух уроков на одной позиции.

## Коллекция `enrollments`

Пример документа:

```js
{
  _id: ObjectId("663000000000000000000001"),
  userId: ObjectId("660000000000000000000004"),
  courseId: ObjectId("661000000000000000000001"),
  status: "ACTIVE",
  progress: {
    completedLessonIds: [ObjectId("662000000000000000000001")],
    percent: 50
  },
  enrolledAt: ISODate("2026-03-21T09:00:00Z")
}
```

Это отдельная коллекция, потому что связь пользователь-курс имеет собственные поля: статус, дата записи, прогресс. Если встроить список курсов в пользователя, станет неудобно получать всех студентов курса. Если встроить список студентов в курс, станет неудобно получать все курсы пользователя. Отдельная коллекция решает обе задачи симметрично.

`progress` сделан embedded document. Он не нужен без enrollment и меняется как часть записи пользователя на конкретный курс.

Индексы:

```js
db.enrollments.createIndex({ userId: 1, courseId: 1 }, { unique: true })
db.enrollments.createIndex({ courseId: 1, status: 1 })
```

Уникальный индекс запрещает повторную запись одного пользователя на один и тот же курс.

## Embedded vs references

Коротко по связям:

- `users.name`, `users.profile` — embedded, потому что это маленькие части пользователя.
- `courses.settings`, `courses.tags` — embedded/array, потому что это свойства курса и они читаются вместе с курсом.
- `lessons.content.blocks` — embedded, потому что блоки принадлежат одному уроку.
- `courses.authorId -> users._id` — reference, потому что один преподаватель связан со многими курсами.
- `lessons.courseId -> courses._id` — reference, потому что уроков может быть много, и они обновляются отдельно.
- `enrollments.userId -> users._id` и `enrollments.courseId -> courses._id` — references, потому что это связь многие-ко-многим с собственными атрибутами.

## Почему MongoDB здесь уместна

Для LMS удобно хранить гибкий контент урока: текстовые блоки, видео, мини-тесты, ссылки, вложения. В реляционной модели это быстро превращается в много таблиц для разных типов блоков. В MongoDB такой контент естественно ложится в документ урока, а основные связи остаются через references там, где это действительно нужно.
