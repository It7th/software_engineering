# performance design для LMS

## 1. Анализ производительности

Система похожа на небольшую LMS: пользователи открывают каталог курсов, смотрят уроки, записываются на курсы и отмечают прохождение уроков.

Частые операции:

- получение списка курсов;
- получение уроков курса;
- получение курсов пользователя;
- поиск пользователя по логину;
- отметка прохождения урока.

Медленные места:

- запросы в MongoDB, особенно aggregation в `GET /users/:userId/courses`;
- поиск по маске имени и фамилии, потому что регулярные выражения могут плохо использовать индекс;
- запись прогресса урока, потому что там есть чтение урока, чтение enrollment, подсчет уроков курса и update;
- потенциально внешние API для LMS тут не реализованы, но в настоящей системе это могли бы быть платежи, email и видео-хранилище.

Примерные требования для учебного API:

- обычные GET-запросы - до 100-200 мс на локальной сети;
- операции записи - до 300-500 мс;
- API должен нормально выдерживать частые открытия каталога и страниц курса;
- один пользователь не должен иметь возможность завалить endpoint прогресса большим количеством запросов.

## 2. Стратегия кеширования

Для этой работы выбран Redis. Он подходит для короткоживущего кеша, быстро очищается и нормально запускается в Docker Compose.

### `GET /courses`

Что кешируется:

- список курсов;
- отдельно кешируется вариант без фильтра и вариант с `status`.

Стратегия:

- Cache-Aside.

TTL:

- 60 секунд.

Почему так:

- каталог читают часто;
- курсы создаются и меняются реже, чем читаются;
- даже если инвалидация не сработает, устаревание максимум на минуту для учебного проекта нормально.

Инвалидация:

- после `POST /courses` удаляются ключи списка курсов.

### `GET /courses/:courseId/lessons`

Что кешируется:

- список уроков конкретного курса.

Стратегия:

- Cache-Aside.

TTL:

- 120 секунд.

Почему так:

- уроки курса часто открываются студентами;
- состав уроков меняется не каждую минуту.

Инвалидация:

- после `POST /courses/:courseId/lessons` удаляется кеш уроков этого курса.

### `GET /users/:userId/courses`

Что кешируется:

- список курсов пользователя вместе с прогрессом.

Стратегия:

- Cache-Aside.

TTL:

- 45 секунд.

Почему так:

- endpoint использует aggregation с `$lookup`;
- данные зависят от записи на курс и прогресса, поэтому TTL короче.

Инвалидация:

- после записи пользователя на курс;
- после отметки урока пройденным.

### `GET /users/by-login`

Что кешируется:

- найденный пользователь по login.

Стратегия:

- Cache-Aside.

TTL:

- 300 секунд.

Почему так:

- login уникальный;
- пользователь по login обычно нужен при авторизации или админских проверках;
- в этой работе нет endpoint изменения login, поэтому риск устаревания маленький.

Инвалидация:

- после создания пользователя удаляется ключ этого login.

## 3. Реализация кеширования

В `src/server.js` добавлены функции:

- `getCachedJson`;
- `setCachedJson`;
- `deleteCachePrefix`.

Логика простая:

1. GET endpoint сначала проверяет Redis.
2. Если ответ найден, API возвращает его с `X-Cache: HIT`.
3. Если ответа нет, API идет в MongoDB, собирает payload, кладет его в Redis и возвращает `X-Cache: MISS`.
4. POST endpoint после успешной записи удаляет связанные ключи.

Это обычный Cache-Aside подход. Он понятный и не ломает основную логику API: MongoDB остается источником истины.

## 4. Проектирование rate limiting

Rate limiting нужен не на все endpoints. На чтение списка курсов я бы не ставил жесткий лимит, потому что это обычное поведение пользователя. Гораздо важнее ограничить операции, которые меняют состояние или могут часто дергаться из клиента.

Endpoints, где rate limiting полезен:

- `POST /users/:userId/lessons/:lessonId/completion` - защита от спама отметками прохождения;
- `GET /users/search` - в реальном проекте можно ограничить, потому что поиск по regex тяжелее обычного запроса;
- `POST /users` - можно ограничить, чтобы не создавать пачки аккаунтов.

В реализации выбран endpoint прохождения урока.

Алгоритм:

- Token Bucket.

Лимит:

- 20 запросов в минуту с одного IP.

Почему Token Bucket:

- он допускает короткий всплеск запросов;
- после всплеска запросы постепенно восстанавливаются;
- для пользовательских действий это удобнее, чем жесткий Fixed Window.

## 5. Реализация rate limiting

Для `POST /users/:userId/lessons/:lessonId/completion` добавлен middleware `tokenBucketRateLimit`.

Состояние bucket хранится в Redis:

- ключ зависит от endpoint и IP;
- в значении лежат `tokens` и `updatedAt`;
- если Redis недоступен, используется локальная память процесса.

При каждом запросе:

1. API восстанавливает часть токенов по прошедшему времени.
2. Если есть хотя бы 1 токен, запрос проходит дальше.
3. Если токенов нет, API возвращает `429 Too Many Requests`.

Заголовки:

- `X-RateLimit-Limit` - общий лимит;
- `X-RateLimit-Remaining` - сколько запросов осталось сейчас;
- `X-RateLimit-Reset` - Unix time, когда bucket восстановится;
- `Retry-After` - сколько секунд подождать при `429`.

## 6. Влияние на производительность

Кеширование снижает количество одинаковых запросов в MongoDB. Для LMS это важно, потому что каталог курсов и уроки открываются намного чаще, чем редактируются.

Что улучшается:

- меньше нагрузка на MongoDB;
- быстрее повторные GET-запросы;
- меньше задержка на aggregation для курсов пользователя;
- API спокойнее переживает всплески чтения.

Rate limiting не ускоряет один отдельный запрос, но защищает сервис от лишней нагрузки. Если клиент случайно отправляет много одинаковых POST-запросов, API перестает тратить ресурсы на обработку каждого из них.

## 7. Метрики для мониторинга

Я бы смотрел такие метрики:

- среднее и p95 время ответа по endpoint;
- количество запросов в секунду;
- количество ошибок `4xx` и `5xx`;
- количество `429`;
- нагрузка на MongoDB;
- количество операций Redis;
- cache hit rate;
- среднее время ответа при `X-Cache: HIT` и `X-Cache: MISS`.

Hit rate можно считать так:

```text
cache_hit_rate = cache_hits / (cache_hits + cache_misses)
```

Для ручной проверки в этой работе можно использовать заголовок `X-Cache`. Например, два раза подряд вызвать `GET /courses`: первый ответ будет `MISS`, второй должен быть `HIT`.

Для нормального мониторинга в проде я бы добавил счетчики:

- `cache_hits_total`;
- `cache_misses_total`;
- `rate_limit_blocked_total`;
- `http_request_duration_seconds`.
